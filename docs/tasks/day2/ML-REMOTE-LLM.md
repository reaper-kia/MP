# ML-15 · LLM на ноуте, приложение на сервере

**Исполнитель:** один человек (ML или TL). **Приоритет:** P0. **Оценка:** 4–6 часов.

## Зачем

Сервер (2 vCPU, 3.8 ГБ, без GPU) не тянет локальную модель, а ноут с GPU тянет
(`qwen2.5:7b-instruct` + `bge-m3`, 100 % GPU). Хотим: приложение крутится на сервере, «мозги»
берутся с ноута. Ноут выключен или без сети → сервер **сам и незаметно для пользователя**
переходит на Yandex API, если и его нет — на эвристики (`stub`).

## Решение (и почему не gRPC до ноута)

```
Ноут (дом / площадка, за NAT)                         Сервер 109.196.167.204
┌──────────────────────────┐   обратный SSH-туннель   ┌─────────────────────────────────────┐
│ Ollama :11434 (GPU)      │ ───────────────────────▶ │ 172.17.0.1:11435 ─▶ ml_service      │
│ autossh (systemd --user) │   ssh -R 172.17.0.1:     │   LLM_PROVIDER=ollama,yandex        │
└──────────────────────────┘   11435:127.0.0.1:11434  │   1) Ollama через туннель (ноут)     │
                                                      │   2) Yandex AI Studio (если ключ)    │
                                                      │   3) эвристики (stub)                │
                                                      │ search_service ─gRPC─▶ ml_service    │
                                                      └─────────────────────────────────────┘
```

- **Ноут за NAT** — сервер к нему напрямую не подключится, поэтому соединение открывает ноут:
  обратный SSH-туннель. Внутри туннеля — HTTP Ollama. Шифрование — SSH, порт наружу не открыт.
- **Почему туннелируем Ollama, а не gRPC `ml_service`:** код ML остаётся один — на сервере, деплоится
  вместе со всем (на ноуте не нужно держать ту же версию `ml_service`); переключение
  «ноут → Яндекс → эвристики» делается внутри одного сервиса, без правок search_service и контрактов.
  gRPC между search_service и ml_service остаётся как был. Вариант «ml_service на ноуте + gRPC через
  туннель + failover в search_service» тоже рабочий, но это два места с логикой переключения и риск
  разных версий кода — его не делаем.

## Сделать

### 1. Туннель (ноут → сервер)
1. **Вход по ключу** (сейчас ключ не принимается, см. TL-15): `ssh -v team-04@109.196.167.204` →
   найти причину (права `~`, `~/.ssh` 700, `authorized_keys` 600, владелец). autossh без ключа не
   работает. Лучше отдельный ключ без passphrase только для туннеля:
   `ssh-keygen -t ed25519 -f ~/.ssh/mp_tunnel -N ""` и в `authorized_keys` на сервере с ограничением:
   `restrict,port-forwarding,permitlisten="172.17.0.1:11435" ssh-ed25519 AAAA… mp-tunnel`.
2. **Сервер — разрешить привязку к адресу docker-моста** (иначе `-R` слушает только 127.0.0.1, а из
   контейнера он недоступен): в `/etc/ssh/sshd_config.d/mp-tunnel.conf` — `GatewayPorts clientspecified`,
   `sudo systemctl reload ssh`. Сделать задачей Ansible (роль `common` или новая `tunnel`), не руками.
3. **Ноут — постоянный туннель**: `autossh` + systemd user unit `infra/tunnel/mp-llm-tunnel.service`:
   ```
   ExecStart=/usr/bin/autossh -M 0 -N -i %h/.ssh/mp_tunnel \
     -o ServerAliveInterval=15 -o ServerAliveCountMax=3 -o ExitOnForwardFailure=yes \
     -R 172.17.0.1:11435:127.0.0.1:11434 team-04@109.196.167.204
   Restart=always
   ```
   Make-цели: `make llm-tunnel-install` (копирует unit, `systemctl --user enable --now`),
   `make llm-tunnel-status`. Порт и адрес — переменные (`TUNNEL_PORT=11435`).
4. Проверка с сервера: `curl -s http://172.17.0.1:11435/api/tags` → список моделей ноута;
   изнутри контейнера: `docker compose exec ml_service python -c "…urlopen('http://host.docker.internal:11435/api/tags')…"`.
5. ufw: 11435 наружу не открывать (слушает только 172.17.0.1 — проверить `ss -ltnp | grep 11435`).

### 2. Цепочка провайдеров в `ml_service`
1. `LLM_PROVIDER` принимает список через запятую: `ollama,yandex` — пробовать по порядку, `stub` всегда
   последний неявно. Один провайдер (`yandex`, `ollama`, `stub`) работает как сейчас. `EMBED_PROVIDER`
   пустой — та же цепочка.
2. `FallbackLLM(providers)`: `available` — есть хоть один доступный; `complete_json` берёт первый
   доступный, на `MlUnavailableError` — следующий. У каждого свой «автомат» (уже есть): упавший
   провайдер 30 с не дёргаем.
3. `FallbackEmbedder` — **внимание:** векторы bge-m3 и Яндекса несравнимы. Внутри одного RPC
   (ScorePosts / GroupPosts) все векторы — от одного провайдера: движок в начале вызова берёт
   `embedder.select()` → конкретный провайдер и работает только с ним; упал посередине — весь вызов
   на следующий провайдер (или без эмбеддингов). Тест: «ollama упал после вектора запроса → векторы
   постов не берутся у Яндекса для того же запроса».
4. **Пороги близости — у провайдера, а не глобальные:** `Embedder.thresholds` (bge-m3 0.38 / 0.68 /
   0.86; Яндекс — из `SIM_*_YANDEX` после калибровки ML-11). `core/scoring.py` и `core/grouping.py`
   получают пороги из выбранного эмбеддера, а не из `core/similarity.THRESHOLDS`.
5. **Быстро понимать, что ноут пропал:** у Ollama-провайдера отдельный `connect`-таймаут 2–3 с
   (`OLLAMA_CONNECT_TIMEOUT_SECONDS`), чтобы уснувший ноут не съедал бюджет 15/45 с;
   read-таймаут — как сейчас.
6. **Пользователь не видит переключения** ollama → yandex: `degraded=false`, ответы те же. В лог —
   `INFO ml provider switched: ollama → yandex (причина)` и в `/health` ml_service — какой провайдер
   сейчас активен (для нас, не для пользователя).
7. Переход на `stub`: по решению TL пользователь не узнаёт. Технически — флаг
   `ML_SHOW_DEGRADED_WARNING` (по умолчанию `true`): при `false` search_service не добавляет
   предупреждение «ML работал в упрощённом режиме». **Риск для оценки:** критерии требуют «отделять
   работающее от имитации» — на демо держать `true` или проговорить это на защите.

### 3. Конфигурация
- Сервер, `.env` (через `env.j2`): `LLM_PROVIDER=ollama,yandex`,
  `OLLAMA_URL=http://host.docker.internal:11435`, `YC_FOLDER_ID`, `YC_API_KEY` (может быть пустым —
  тогда цепочка ollama → stub).
- Ноут (локальный стенд) — как сейчас: `LLM_PROVIDER=ollama`, `OLLAMA_URL=http://host.docker.internal:11434`.
- `group_vars`: `llm_provider: "ollama,yandex"`; `env.j2` — `OLLAMA_URL` и `OLLAMA_CONNECT_TIMEOUT_SECONDS`.

## Тесты
- `FallbackLLM`: первый упал → ответ второго; все упали → `MlUnavailableError` → движок отвечает
  эвристикой; первый «выключен автоматом» → сразу второй, без запроса к первому.
- `FallbackEmbedder` + движок: один RPC — один провайдер (п. 2.3); пороги берутся от провайдера (п. 2.4).
- Настройки: `LLM_PROVIDER=ollama,yandex` парсится; неизвестное имя → понятная ошибка на старте.

## DoD
1. Туннель поднят systemd-юнитом и переживает перезагрузку ноута и пропадание сети (autossh переподключается за ≤ 30 с).
2. На сервере поиск «Безопасность дорожного движения в Красноярском крае» с включённым ноутом:
   в логах ml_service — `ollama`, `degraded=false`, на ноуте `ollama ps` → модель на GPU.
3. Выключили Wi-Fi на ноуте посреди поиска → поиск завершается; следующие вызовы — `yandex` (если
   ключ) или эвристики; пользователь видит обычную подборку.
4. Включили ноут → в течение ~1 минуты снова `ollama`.
5. `make check` зелёный; README ML + раздел «Модели» в корневом README: схема, что куда уходит
   (тексты постов — на ноут команды через SSH), что будет без ноута.

## Риски
- Ноут на площадке за чужим Wi-Fi может блокировать исходящий SSH (22) — проверить заранее; запасной
  вариант — sshd на сервере дополнительно слушает 443.
- Ноут уснул → TCP висит до таймаута: поэтому короткий connect-таймаут и `ServerAliveInterval`.
- Две параллельные нагрузки на GPU (локальный стенд + сервер) делят видеокарту: на демо гасить
  локальный стенд или учитывать.
