# B2 — поиск и подборка, день 2

Зона: `services/search_service`. Критерии: «Достоверность и учёт» (10), готовность сценариев 3–5,
цифры для слайда «Качество и время».

Что выяснили сегодня: с моделью на одной видеокарте поиск по ~13 источникам идёт 3–5 минут; когда
параллельно идут 2–3 поиска, `analyzing_query` упирается в бюджет 15 с и уходит в эвристику, smoke не
укладывается в 180 с. Уже поменяли: search_service передаёт сборщику `max_posts=0` (лимиты сборщика:
150 на источник, 200 на «везде», `DEFAULT_MAX_POSTS_*` в compose).

### [ ] B2-15 · P0 · один поиск за раз
**Цель.** На показе и у экспертов второй поиск не должен ломать первый (GPU / CPU одни на всех).

**Сделать.** Глобальный семафор на пайплайн (`SEARCH_CONCURRENCY`, по умолчанию 1): новый поиск,
пока идёт другой, остаётся в `status=queued`, `stage=queued` (стадия уже есть в контракте) и
стартует сам, когда освободится место. Отмена в очереди работает. Перезапуск сервиса — как сейчас.

**DoD.** Тест на фейках: два поиска подряд — второй `queued`, пока первый не завершился; вживую два
поиска с сайта — оба доходят до финала, у второго в интерфейсе «В очереди…».

### [ ] B2-18 · P0 · учёт повторов на реальных данных
**Цель.** «Повтор того же поста не увеличивает счётчик» — главный пункт достоверности.

**Сделать.** На реальном VK: один и тот же пост приходит из источника и из «везде» (через Яндекс) и
по двум поисковым фразам → одна запись; «Повторить» неудачные цели → счётчик не растёт; одна новость
в трёх группах → три записи и один сюжет. Проверить нормализацию ссылки (vk.com / vk.ru / m.vk.com,
`wall-123_45` и `?w=wall-123_45`) — разные формы одного поста не должны давать две записи.

**DoD.** Тест на нормализацию ссылок; вживую — числа сходятся, протокол в `docs/demo/README.md`.
