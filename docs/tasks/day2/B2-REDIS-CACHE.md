# B2-20 · Кэш в Redis: одинаковый поиск — сразу, сбор — без повторных походов в VK/OK

**Исполнитель:** один человек (B2; часть в collector — по договорённости с B1). **Приоритет:** P1.
**Оценка:** 5–7 часов.

## Зачем

Поиск с моделью идёт 1–5 минут и нагружает сервер, VK и OK. Если кто-то (или расширение FE-17) ищет
то же самое, что уже искали недавно, — подборка должна появиться **сразу**. Похожие поиски по тем же
источникам не должны заново выкачивать стены групп.

## Два уровня

| Уровень | Где | Ключ | Что лежит | TTL по умолчанию |
|---|---|---|---|---|
| **1. Готовая подборка** | search_service | хэш нормализованных параметров поиска | `search_id` готового поиска | `CACHE_SEARCH_TTL_SECONDS=1800` (30 мин) |
| **2. Сбор** | collector_service | площадка + источник + период (или фразы + период для «везде») | посты (`RawPost`) | `CACHE_COLLECT_TTL_SECONDS=600` (10 мин) |

Оценки ML не кэшируем (решение TL).

## Уровень 1 — готовая подборка

1. **Ключ:** `mp:search:v1:{sha256(json)}`, где json — нормализованные параметры:
   запрос (`strip`, пробелы схлопнуты, нижний регистр), `period_from`, `period_to`, `mode`,
   отсортированные `platforms`, отсортированные `source_ids` (только в `selected`). Другой период,
   источник или площадка — другой ключ, подборки не смешиваются.
2. **Пишем** при финале поиска со статусом `completed` или `partial` (не `failed` / `cancelled`).
3. **Читаем** в `POST /searches`: ключ есть, исходный поиск существует →
   **не возвращаем тот же `search_id`, а копируем поиск**: новая запись `Search` с теми же параметрами,
   статусом, целями (`targets`), результатами и группами, у результатов `excluded=false`, счётчики
   пересчитаны. Почему копия: исключения и повторы одного пользователя не должны появляться у
   другого. Копирование — одним `INSERT … SELECT` в транзакции, это миллисекунды.
4. У копии поля `cached_from_search_id` и `cached_at` (время исходного финала) — миграция Alembic.
   Контракт (через TL): в `Search` (proto + `openapi.yaml`) — `cache: {from_search_id, created_at} | null`.
5. **Обход кэша:** в `SearchCreateIn` поле `fresh: bool = false`. `true` — не читаем кэш (пишем как
   обычно). Кнопки «Повторить» и «Обновить» на фронте шлют `fresh=true`.
6. **Фронт (с FE):** у подборки из кэша плашка в полосе параметров:
   «Подборка из кэша · собрана 12 мин назад · Обновить» → тот же поиск с `fresh=true`. Так ТЗ
   «понятно, к каким параметрам и моменту относится подборка» выполнено.
7. **Одинаковый поиск уже идёт** (P2): ключ `mp:search:running:{hash}` → новый поиск ждёт в очереди
   (B2-15) и после финала первого получает копию.

## Уровень 2 — сбор (collector)

1. В collector уже есть порт кэша и `CachingBehavior` (в памяти, для `ResolveSource`). Сделать
   адаптер `RedisCache` с тем же портом и включить поведение для `CollectFromSource` и
   `SearchPlatform`.
2. **Ключи:** `mp:collect:v1:{platform}:{source_external_id}:{period_from}:{period_to}:{max_posts}`;
   `mp:psearch:v1:{platform}:{sha256(отсортированные фразы)}:{period}:{max_posts}`.
   Значение — список постов JSON (zlib, если > 64 КБ).
3. Кэшируем только **успешный** полный ответ; ошибка площадки или неполный сбор (бюджет 50 с кончился)
   — не кэшируем.
4. `ResolveSource` — переложить в тот же Redis (`CACHE_RESOLVE_TTL_SECONDS`, сейчас 600 в памяти),
   чтобы кэш переживал перезапуск сервиса.

## Настройки — меняются в `.env` за пару кликов

```
CACHE_ENABLED=true                 # false — кэш выключен целиком, всё работает как раньше
REDIS_URL=redis://redis:6379/0
CACHE_SEARCH_TTL_SECONDS=1800      # готовая подборка
CACHE_COLLECT_TTL_SECONDS=600      # посты источника / поиск по площадке
CACHE_RESOLVE_TTL_SECONDS=600      # карточка источника по ссылке
REDIS_MAXMEMORY=256mb              # потолок памяти Redis на сервере (3.8 ГБ всего)
```

- `compose.yaml`: сервис `redis` (`redis:7-alpine`, `command: redis-server --maxmemory ${REDIS_MAXMEMORY:-256mb} --maxmemory-policy allkeys-lru --save ""`,
  healthcheck `redis-cli ping`, порт наружу не публиковать); переменные в `search_service` и
  `collector_service`. `.env.example` — блок выше с комментариями.
- Ansible: `redis:7-alpine` в `docker_base_images` (`group_vars`), `CACHE_*` в `env.j2` — по образцу
  `YC_API_KEY` (значение из окружения или по умолчанию).
- После смены TTL: `docker compose up -d search_service collector_service`. Сбросить кэш:
  `docker compose exec redis redis-cli FLUSHDB` → цель `make cache-flush`.

## Надёжность

- **Redis упал или недоступен → поиск работает без кэша** (fail-open): ошибка в лог (`WARNING cache
  unavailable`), не в ответ пользователю. `/health/ready` показывает `redis: up/down`, но не валит
  готовность.
- Таймаут обращения к Redis — 200 мс.
- Логи: `cache hit` / `cache miss` / `cache store` с уровнем и ключом (без текста запроса), для
  слайда — доля попаданий (B2-11).

## Тесты
- Нормализация ключа: «  ДТП   Красноярск » и «дтп красноярск» — один ключ; другой период / источник /
  площадка — другой.
- Попадание: второй `POST /searches` с теми же параметрами → новый `search_id`, сразу финальный статус,
  те же публикации, `excluded=false`, `cache.from_search_id` заполнен; исключение в копии не меняет
  исходный поиск.
- `fresh=true` → пайплайн запускается.
- `failed` / `cancelled` в кэш не попадают.
- Collector: второй `CollectFromSource` с тем же ключом не вызывает коннектор; ошибка коннектора не
  кэшируется.
- Redis недоступен (фейк кидает исключение) → поиск проходит, в логе warning.

## DoD
1. Один и тот же запрос второй раз (сайт или расширение) — подборка за < 1 с, плашка «из кэша», число
   публикаций совпадает с первым; «Обновить» запускает настоящий поиск.
2. Тот же запрос с другими источниками или периодом — настоящий поиск, не кэш.
3. Похожий запрос по тем же источникам в пределах 10 мин — стадия сбора секунды, в логе collector
   `cache hit`.
4. `CACHE_ENABLED=false` → всё как до задачи; `docker compose stop redis` → поиск работает.
5. TTL меняется в `.env` и применяется после `docker compose up -d …`.
6. `make check` зелёный, миграция применяется на чистой БД и на базе сервера; README: раздел
   «Кэш» (что кэшируется, сколько живёт, как выключить и сбросить).
